MCP and AI assisted debugging

Rails Profiler ships an MCP server. Your AI coding assistant lists the profiles of your running Rails app, opens the one you are talking about and reads the sections it needs, instead of you pasting the SQL tab, the logs or the response body into the conversation.

From the root of the Rails application, for Claude Code:

claude mcp add rails-profiler -- bundle exec rake profiler:mcp

A real session: finding and fixing an N+1

The question: /api/n_plus_one feels slow, can you find out why and fix it? Below are the tool calls an assistant makes for it, and excerpts of what the tools returned, quoted from the gem's MCP guide. They were made against the gem's demo application, whose endpoint loads ten posts and then each post's author one query at a time, with the MCP Inspector command line client over stdio. Headings and footers are left out, cuts are marked [...], and timings and tokens change from one run to the next.

  4. Explain the repeated query

    get_profile numbers the queries from 1, explain_query counts from 0: "Query 2" is query_index: 1. On SQLite the plan is EXPLAIN QUERY PLAN's:

    Adapter: `sqlite`

```
3	0	33	SEARCH authors USING INTEGER PRIMARY KEY (rowid=?)
```

    Each lookup already uses the primary key: no index is missing, the cost is the number of round trips. The fix is to load the authors together with the posts.

  5. Fix it

    Line 78 of the controller:

    -    posts = Post.all.to_a
+    posts = Post.includes(:author).to_a

Step 5 is not an MCP call: an assistant that edits your code does so with its own tools. The MCP server reads what the profiler recorded, it never opens or writes a file.

What the assistant can read and change

The server has 21 tools and 7 resources. They read every profile the profiler stored (requests, background jobs, console expressions and tests, section by section: database, performance timeline, cache, views, logs, outgoing HTTP, mailers and more), the same data as the dashboard, after masking. Tools marked write change something.

Requests and profiles
query_profiles, get_profile, get_profile_ajax, get_profile_http, get_profile_dumps, get_profile_mailers, query_mailers, clear_profiles (write); resource profiler://recent
SQL
analyze_queries (N+1 patterns, duplicates, slow queries), explain_query; resources profiler://slow-queries, profiler://n1-patterns
Background jobs
query_jobs, get_profile (on a job's token); resource profiler://recent-jobs
Tests
query_test_profiles, get_test_profile, run_tests (write: runs the test files the profiler discovered); resources profiler://slow-tests, profiler://failing-tests
Console
query_console_profiles; resource profiler://recent-console
ENV variables
list_env_vars, set_env_var (write), delete_env_var (write), reset_env_var (write), reset_all_env_vars (write)
Cluster
list_slaves (and a slave parameter on every other tool)

What it cannot do

  • Query your database. No tool takes SQL: explain_query takes a profile token and the index of a query that profile recorded, and only explains read-only statements, in a transaction always rolled back.
  • Read or change your code. It sees file names and line numbers in backtraces, template names and logs, not the files.
  • Make requests to your application. You, your browser, your jobs or your tests produce the profiles; the only thing it can start is a run of discovered test files.
  • See masked values. Parameters matched by config.filter_parameters and ENV variables outside config.env_allowlist are stored masked: the assistant gets the mask, not the value.

Two transports

stdio

What runs
A process the MCP client starts, bundle exec rake profiler:mcp, in the application's directory.
Configuration
None.
Network
None: the client talks to the process over its standard input and output, and only that client can reach it.
Profiles it reads
Those of the profile store, which must be one other processes can read (:file, :sqlite or :redis).

HTTP

What runs
The application itself, which answers at /_profiler/mcp.
Configuration
Opt in: the route exists only with config.mcp_enabled = true and config.mcp_transport = :http, and answers 404 otherwise.
Network
An endpoint behind the same access control as the dashboard, plus Host, Origin and Content-Type checks; a request that fails one gets a 403.
Profiles it reads
Those of the running application.
# config/initializers/profiler.rb
Profiler.configure do |config|
  config.mcp_enabled = true
  config.mcp_transport = :http
end

Security

  • The profiler, and so the MCP server, is on in development and test and off everywhere else unless you enable it explicitly.
  • Over HTTP, every MCP request goes through the same access control as the dashboard: by default (authorization_mode: :allow_local) only requests from this machine get in.
  • ENV overrides saved through MCP or the dashboard are never applied in production, nor while the profiler is disabled.
  • The write tools are part of the same server: whoever passes these checks can change ENV, clear profiles and run tests, unless the server is read-only.

Read-only mode leaves out the six tools marked write above. For a stdio process, the environment variable PROFILER_MCP_READ_ONLY=1 does the same:

# config/initializers/profiler.rb
Profiler.configure do |config|
  config.mcp_read_only = true
end

Setup for Claude Desktop and other clients, every tool's parameters and the cluster mode are in the MCP server guide.
