What Rails Profiler shows you, when you need it

Four everyday moments of debugging a Rails app, and the part of the profiler you open for each. Every request gets a profile, reached from the debug toolbar at the bottom of the page or from the dashboard at /_profiler.

  • An N+1 in the SQL
  • The flame graph
  • Cache hits and misses
  • A background job

Spot the N+1 hiding in a page's queries

The Database tab lists every SQL query of the request in order: its number, the model, the time it took and the SQL with the bind values replaced by ?. That last detail is what makes repetition visible. When the same parameterized query runs 3 times or more, the tab warns about an N+1, groups the pattern, highlights it and gives you the backtrace behind it.

A summary tops the list: total count, total duration, slow queries and cached ones. Anything above slow_query_threshold (100 ms by default) is marked in red. The Explain button shows a query's plan, for read-only queries only and in a transaction that is always rolled back.

Prefer to ask? The MCP server's analyze_queries tool gives an AI assistant the same reading of a request.

Read where a request spends its time

The Timeline tab draws every instrumented event of the request as a flame graph: controller, views, partials, SQL, cache, outbound HTTP and your own blocks, each nested under what called it. Click a block to zoom in, scroll to zoom, drag to pan, hover for the name, duration and payload, and press Ctrl+F to highlight matching events.

Wrap any slow piece of code in Profiler.measure("pricing.quote") and it appears at its place in the hierarchy.

Below the events, function profiling shows which Ruby methods the request spent its time in. Lite mode samples with the stackprof gem, which you add to your Gemfile yourself; full mode traces every method call with a TracePoint, with allocations and memory per method.

See which cache reads hit and which missed

The Cache tab lists each key the request read, with a HIT or MISS badge and how long the read took. When a page you expected to be cached is still slow, this is where the miss shows up, key by key.

Its summary counts reads, writes and deletes and gives the hit rate, shown in green above 80%. Writes and deletes are counted there but not listed. The toolbar carries the same hit rate in its CACHE item, which only appears when the request read the cache.

Follow a failed job back to the request that queued it

With config.track_jobs = true, the default, every ActiveJob and Sidekiq job gets a profile of its own: SQL, cache, outbound HTTP, logs and exceptions, its queue, its arguments (masked like request parameters), its status and its error.

A request that enqueued jobs lists them in its Jobs tab, mails sent with deliver_later included, with View Job to open each one. The job profile names the request or job that queued it under Triggered by, with a link back. A job that raised opens straight on its Exception tab, and the toolbar's JOB item turns red when a job of the page failed.
